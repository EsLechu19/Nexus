# Spec 008 — Frontend Movimientos de Inventario (Alta y Historial)

## Contexto y objetivo
La tienda necesita registrar y auditar los movimientos de inventario desde la interfaz web, apoyándose en el esqueleto base de `005-frontend-base` (layout, cliente API centralizado y componentes base de cargando/error/vacío) y en los catálogos ya gestionados en `006-frontend-productos` y `007-frontend-proveedores`. Esta funcionalidad entrega exclusivamente la pantalla de movimientos que consume el backend definido en `003-movimientos-inventario`: alta de movimientos de entrada (con producto y proveedor obligatorios) y de salida (solo con producto), más la consulta del historial en modo solo lectura append-only. No incluye edición ni baja de movimientos, ni cálculo/visualización de stock actual. Es consumidora directa de `001` y `002` para la selección de producto/proveedor y predecesora de `009-frontend-stock`, donde se visualizará el stock derivado.

## Usuarios
- **Encargado de inventario:** registra entradas y salidas y consulta el historial para auditar. Único actor del MVP. Sin autenticación ni roles; mismo operador de tienda de `005`/`006`/`007`.

## Historias de usuario
- **HU-1:** Como encargado, quiero ver el historial completo de movimientos ordenado cronológicamente para auditar entradas y salidas sin filtros.
- **HU-2:** Como encargado, quiero registrar una entrada de stock indicando producto, proveedor, cantidad y motivo opcional para aumentar el stock de forma trazada.
- **HU-3:** Como encargado, quiero registrar una salida de stock indicando producto, cantidad y motivo opcional para disminuir el stock sin permitir negativo.
- **HU-4:** Como encargado, quiero entender qué pasó cuando un alta o la carga del historial falla para corregir o reintentar sin perder contexto.

## Requisitos funcionales

### RF-1 — Historial de movimientos en solo lectura
El sistema debe mostrar el historial completo de movimientos en modo solo lectura, sin filtros UI, sin paginación y sin edición/baja.
- **Criterios de aceptación (EARS):**
  - Cuando el encargado acceda a la sección movimientos, el sistema deberá pedir el historial a la API (`GET` sin filtros) y mostrar todos los movimientos tal cual los devuelve la API ordenados por `fecha desc + id desc`, sin reordenar en el frontend, sin filtros en UI, sin paginación y con scroll vertical si crece y sin truncar.
  - Mientras se espera la respuesta, el sistema deberá mostrar el estado cargando uniforme con texto "Cargando...".
  - Cuando la API devuelva lista vacía, el sistema deberá mostrar el estado vacío con mensaje "Sin datos disponibles".
  - Cuando la API responda con error 4xx, el sistema deberá mostrar el mensaje específico devuelto por la API sin botón Reintentar; cuando sea error de red, timeout o 5xx, deberá mostrar "Error de conexión con el servidor" con botón "Reintentar" que reejecute solo la carga del historial.
  - Cuando `proveedor` o `motivo` sean `null` en la respuesta, el sistema deberá mostrar un guion "—" en esa celda; el historial es puramente de lectura, no ofrece acciones por fila.
  - El sistema deberá mostrar 7 columnas fijas `fecha | producto | proveedor | tipo | cantidad | motivo | id` sin columna de estado y sin interacción más allá de visualizar; no deberá mostrar `stock_actual` en esta pantalla (reservado para `009`). La columna `fecha` muestra el `created_at` UTC ISO8601 tal cual lo entrega la API sin formateo localizado; `motivo` largo se muestra completo sin truncar con salto de línea; si hay cientos/miles de filas, el historial hace scroll vertical sin virtualización en el MVP.

### RF-2 — Alta de movimiento de entrada
El sistema debe permitir registrar una entrada de stock mediante formulario modal con selección de producto y proveedor.
- **Criterios de aceptación (EARS):**
  - Cuando el encargado accione "Crear movimiento", el sistema deberá abrir un formulario modal con selector de tipo `Entrada | Salida` (tabs/radio) preseleccionado en `Entrada`, y para `Entrada` mostrar campos `producto` (`<select>` requerido), `proveedor` (`<select>` requerido), `cantidad` (texto/número requerido) y `motivo` (texto opcional).
  - Los `<select>` de `producto` y `proveedor` deberán cargarse desde `/api/v1/productos` y `/api/v1/proveedores` respectivamente, mostrando solo activos ordenados por `codigo` con texto de opción `${codigo} — ${nombre}` y placeholder `Selecciona producto` / `Selecciona proveedor`; mientras cargan mostrarán `disabled` con opción `Cargando...`; no se permite texto libre para evitar errores de formato o código inexistente.
  - Si `producto` o `proveedor` no tienen opciones disponibles (`[]`), el sistema deberá bloquear el botón "Crear" y mostrar dentro del formulario un mensaje puntual bajo el `<select>` correspondiente: "No hay productos activos disponibles. Crea un producto primero." o "No hay proveedores activos disponibles. Crea un proveedor primero.", sin permitir envío; el bloqueo es por tipo: `Entrada` requiere ambos, `Salida` solo `producto`.
  - Si la carga de `producto` o `proveedor` falla, el sistema deberá mostrar dentro del modal un `ErrorMessage` correspondiente y mantener el formulario bloqueado: si es `4xx` (incluido `401`) sin botón Reintentar, el usuario puede cerrar el modal y al reabrirlo se reintentará la carga; si es `5xx`/red con botón Reintentar, Reintentar reejecuta solo la carga de los `<select>` sin cerrar el modal.
  - Si `producto`, `proveedor` o `cantidad` están vacíos tras `trim`, o `cantidad` no es entero mayor a `0`, o `motivo` se informa y queda vacío tras `trim` (`""`/`"   "`), el sistema deberá señalar error de forma sin llamar a la API; el frontend valida solo presencia tras `trim` + `cantidad >0 entero` con regla: tras `trim`, debe coincidir con `/^-?\d+$/` y `Number.isInteger(Number(valor)) && Number(valor) > 0`; ejemplos: `" 5 "` → `5` válido, `"001"` → `1` válido, `"1.0"` / `"-1"` / `"0"` / `"1,5"` / `"abc"` → "Debe ser un número entero mayor a 0"; para `motivo`, si se informa y `trim() === ""` → "No puede quedar vacío" (ej. `" a "` → se envía `"a"` y deja que backend responda `422` por longitud `1`); no valida límite superior `1_000_000`, longitudes `2-200` de `motivo` ni `\n` — esas reglas las decide el backend y el mensaje `422` se muestra tal cual; al cambiar de tipo `Entrada↔Salida` los errores previos de validación se limpian.
  - Cuando el encargado envíe el formulario con forma válida, el sistema deberá enviar la entrada a la API y deshabilitar el botón "Crear" mientras la petición está en curso.
  - Si la API responde con error `4xx` (ej. `404` producto/proveedor no existe, `400` inactivo, `422` cantidad/motivo), el sistema deberá mantener el modal abierto y mostrar el mensaje específico devuelto por la API sin Reintentar.
  - Si la API responde con error de red, timeout o `5xx`, el sistema deberá mantener el modal abierto y mostrar "Error de conexión con el servidor" con `Reintentar` que reejecute solo el alta de entrada.
  - Cuando la API confirme alta exitosa (`201`), el sistema deberá cerrar el modal, mostrar mensaje breve "Movimiento registrado correctamente" como banner dentro de la pantalla sobre el historial (con `role="status"` `aria-live="polite"`, visible 3 segundos, distinto de `ErrorMessage`, posicionado inmediatamente encima del historial; si hay un banner previo visible, su temporizador se reinicia y muestra el nuevo mensaje por 3s), y revalidar el historial pidiéndolo de nuevo a la API sin persistencia en cliente; si la revalidación posterior falla, se mantendrá el banner de éxito visible sus 3s y además se mostrará el error del listado debajo del banner con Reintentar (ambos coexisten, banner arriba, `ErrorMessage` debajo).

### RF-3 — Alta de movimiento de salida
El sistema debe permitir registrar una salida de stock mediante el mismo formulario modal, sin requerir proveedor.
- **Criterios de aceptación (EARS):**
  - Cuando el encargado seleccione tipo `Salida` en el modal, el sistema deberá mostrar solo `producto` (`<select>` requerido), `cantidad` (requerido) y `motivo` (opcional), ocultando el campo `proveedor` y sin enviarlo en el payload aunque hubiera sido completado previamente en `Entrada`.
  - Si el usuario cambia de `Entrada` a `Salida` después de haber rellenado campos, el sistema deberá conservar `producto`, `cantidad` y `motivo` ya escritos y limpiar cualquier error de validación previo asociado a `proveedor`, y limpiar/ocultar `proveedor` para evitar envío erróneo; al volver de `Salida` a `Entrada`, `proveedor` deberá quedar vacío nuevamente y requerir nueva selección, conservando `producto/cantidad/motivo` y limpiando errores previos.
  - Si `producto` o `cantidad` están vacíos tras `trim`, o `cantidad` no es entero `>0`, o `motivo` informado queda vacío tras `trim`, el sistema deberá señalar error de forma sin llamar a la API (mismo criterio que RF-2).
  - Cuando el encargado envíe la salida con forma válida, el sistema deberá enviar solo `producto`, `cantidad` y `motivo` (sin `proveedor`) a la API y deshabilitar "Crear" mientras la petición está en curso.
  - Si la API responde con `4xx` (ej. `404` producto no existe, `400` producto inactivo, `400` stock insuficiente cuando `cantidad > stock_actual`, `422` cantidad/motivo), el sistema deberá mantener el modal abierto y mostrar el mensaje específico sin Reintentar.
  - Si la API responde con red/timeout/`5xx`, el sistema deberá mantener el modal abierto y mostrar "Error de conexión con el servidor" con `Reintentar`.
  - Cuando la API confirme salida exitosa (`201`), el sistema deberá cerrar el modal, mostrar el mismo banner "Movimiento registrado correctamente" 3s y revalidar el historial; si la revalidación falla, coexistencia de banner y error de listado como en RF-2.

### RF-4 — Manejo uniforme de estados y revalidación
El sistema debe reutilizar los patrones base de `005` y garantizar revalidación sin caché para movimientos.
- **Criterios de aceptación (EARS):**
  - Mientras cualquier operación (carga de historial o alta de entrada/salida) esté en curso, el sistema deberá deshabilitar su botón disparador para evitar envíos duplicados locales por doble clic; este deshabilitado no evita concurrencia distribuida entre pestañas/usuarios, que se resuelve mostrando el `4xx` específico de la API.
  - Cuando el encargado informe `cantidad` vacía o no entera `>0`, o `motivo` informado y vacío tras `trim`, el sistema deberá bloquearlo localmente como error de forma sin llamar a la API (incluye `null`/ausente vs `""`).
  - Cuando una operación concurrente sea rechazada por la API (ej. alta con producto/proveedor que pasó a inactivo entre carga del `<select>` y envío, o salida con stock insuficiente por concurrencia), el sistema deberá mostrar el mensaje `4xx` específico devuelto sin lógica de bloqueo adicional en el frontend y sin refrescar automáticamente el `<select>` (el valor inactivo permanece seleccionado hasta cerrar/reabrir el modal, donde se recargará).
  - Cuando cualquier alta modifique el historial con éxito, el sistema deberá revalidar el historial pidiéndolo de nuevo a la API sin usar `localStorage`/`sessionStorage`; como no existe ningún filtro aplicado, la revalidación simplemente vuelve a pedir el listado completo; si la revalidación falla con `401`/`red`/`5xx`, se mostrará el error del listado correspondiente manteniendo el banner de éxito (coexistencia 3s) con `401` como `validacion` sin Reintentar y `5xx/red` con Reintentar.
  - Si la API responde con `401`, el sistema deberá tratarlo como cualquier otro `4xx` mostrando el mensaje de la API sin redirección y sin Reintentar; si la revalidación posterior falla con `401`, se mostrará como `ErrorMessage` validacion sin Reintentar además del éxito.
  - Si el historial está `cargando` y el usuario abre el modal de alta, el historial permanece en `Cargando...` de fondo; al confirmar el alta, la revalidación posterior esperará a que termine la carga en curso sin cancelar la petición en curso; `ESC` y navegación durante `alta` en curso se ignoran y la petición se mantiene sin deshabilitar navegación global.

## Requisitos no funcionales
- **RNF-1 — Fuente de verdad API:** el frontend valida solo `cantidad` requerida y entero `>0` (`/^-?\d+$/` + `Number.isInteger` tras `trim`) y `motivo` no vacío tras `trim` si se informa; `producto`/`proveedor` formato `^[A-Z0-9_-]{3,20}$` y `activo`, `cantidad` rango `1..1_000_000` y `motivo` `2-200` sin `\n` los decide el backend y sus mensajes se muestran tal cual sin anticipar; conteo de longitud para `motivo` es por `String.length` simple (no Unicode grapheme).
- **RNF-2 — Reutilización de base 005/006/007:** historial y formulario usan `Loading` ("Cargando..."), `EmptyState` ("Sin datos disponibles") y `ErrorMessage` con dos niveles (4xx sin Reintentar vs red/5xx con Reintentar) sin variantes; mensajes de éxito son banners breves separados (`role="status"` `aria-live="polite"` 3s), mismo patrón que `006`/`007`; la mención de `ErrorMessage`/`Loading` en esta spec es solo a nivel de comportamiento reutilizado de `005`, no prescribe nombres de archivos ni arquitectura, que se definirán en `plan.md`.
- **RNF-3 — Estado solo en memoria:** sin persistencia en cliente (`localStorage`/`sessionStorage` prohibidos para inventario); todo dato se revalida contra la API tras mutación (constitución frontend §5); conservar `producto/cantidad/motivo` al cambiar de tipo `Entrada↔Salida` es estado efímero en memoria del modal, no persistencia.
- **RNF-4 — Mantenibilidad junior:** flujo modal en misma pantalla, sin paginación/búsqueda, sin estado global, con selector de tipo `Entrada|Salida` que condiciona campos y conserva valores al cambiar de tipo salvo `proveedor` que se limpia al ocultar; errores de validación se limpian al cambiar de tipo.
- **RNF-5 — Mensajes en español:** navegación, placeholders, errores y éxitos breves en español; los dos genéricos de `005` sin variantes; los mensajes `4xx` de `003` ya son en español, por lo que mostrarlos tal cual no viola idioma; si un `422` llegara en otro idioma, se mostrará tal cual sin traducir y sin exponer stack, sin violar constitución §6 porque la fuente de verdad es `003` que garantiza español.
- **RNF-6 — Accesibilidad mínima:** formulario modal con `label` asociado a cada input/`select` (`htmlFor`/`id`), foco visible, navegación por teclado, `role="dialog"` para modal y `role="alert"` para errores; selector de tipo accesible por teclado (`radio`/`tabs` con roving tabindex); botón "Borrar" no aplica aquí; no se exige WCAG completo.

## Casos límite
- Historial vacío legítimo → `EmptyState`; transición de 0 a 1 tras primera alta revalidada muestra tabla manteniendo banner éxito 3s; historial con muchos movimientos (cientos/miles) hace scroll vertical sin paginación ni virtualización en MVP.
- Historial con error `4xx` sin mensaje o cuerpo no JSON → genérico validación "No se pudo completar la solicitud. Revisa los datos e intenta nuevamente." sin Reintentar; `5xx`/red → genérico conexión con Reintentar.
- Carga inicial del historial falla con `401` → `ErrorMessage` validacion sin Reintentar, sin `EmptyState`, historial no visible; botón `Crear movimiento` permanece habilitado (no depende del historial) y al abrir el modal los `<select>` intentan cargarse independientemente.
- `<select>` de `producto` o `proveedor` vacío `[]` → botón "Crear" bloqueado con mensaje puntual dentro del formulario indicando que no hay activos disponibles (diferenciado por tipo: `Entrada` bloquea si falta cualquiera, `Salida` solo si falta `producto`).
- Carga de `<select>` falla con `401` → `ErrorMessage` validacion sin Reintentar dentro del modal, formulario bloqueado; el usuario puede cerrar el modal y al reabrirlo se reintenta la carga automáticamente (no queda bloqueado permanentemente); con `5xx`/red → `ErrorMessage` conexion con Reintentar que reejecuta solo la carga del `<select>` fallido.
- Alta `entrada` con `producto`/`proveedor` que pasa a `inactivo` entre carga del `<select>` y envío, o `salida` con stock insuficiente por concurrencia → backend `400`/`404`, frontend mantiene modal con mensaje específico sin Reintentar y sin refrescar automáticamente el `<select>` (valor inactivo permanece seleccionado hasta cerrar/reabrir).
- `cantidad` `0`, `-1`, `1.5`, `"10"` como string, `1000001`, `"001"` → `1` válido, `"1.0"` → "Debe ser un número entero mayor a 0"; frontend solo bloquea vacío/`<=0`/no entero (`" 5 "` → `5` válido, `" 001 "` → `1` válido), deja el límite superior `1_000_000` al backend (`422`).
- `motivo` `""`/`"   "`/`1`/`201`/`\n`/`Ñ`/`emoji`/`null`/ausente → frontend solo bloquea `""`/`"   "` si se informa, resto `422` del backend tal cual; `null`/ausente se omite y se acepta; conteo por `length` simple, no por grapheme.
- Cambio de tipo `Entrada`→`Salida` con `producto`/`cantidad`/`motivo` ya rellenados → se conservan y se limpian errores previos de validación; `proveedor` se oculta/limpia y no se envía; volver a `Entrada` deja `proveedor` vacío requiriendo nueva selección.
- Múltiples clics rápidos en `Crear` → botón `disabled` mientras `cargando`, sin duplicados locales; concurrencia distribuida resuelta vía `4xx` específico.
- Revalidación del historial falla con `red`/`5xx`/`401` tras alta exitosa → se mantiene éxito 3s y se muestra además `ErrorMessage` del listado debajo del banner con Reintentar (si `401`, sin Reintentar).
- Cierre de modal/navegación mientras alta está en curso → petición no se cancela, `ESC` ignorado durante `cargando` sin deshabilitar navegación global, al volver se revalida y se muestra resultado; si historial estaba `cargando` en paralelo, la revalidación espera sin cancelar la carga en curso.
- `401` en alta o en revalidación del historial → tratado como `4xx` estándar sin redirección, sin Reintentar.

## Fuera de alcance
- Búsqueda, filtros UI, paginación, ordenamiento distinto a `fecha desc + id desc` y valorización; el historial se muestra completo con scroll vertical (backend no pagina).
- Edición, borrado, reactivación o borrado físico de movimientos ya registrados; el historial es `append-only` y solo se permite alta y consulta.
- Visualización de `stock_actual` o cálculo de stock en esta pantalla; reservado para `009-frontend-stock` (tal como delimita `003`).
- Gestión de `stock_inicial`, categorías, productos/proveedores inactivos más allá de no listarlos en `<select>`; la baja de catálogos no se gestiona aquí.
- Reservas, lotes, caducidad, ubicaciones de almacén, costes/precios y reportes agregados.
- Filtros avanzados por fecha, reportes y paginación por defecto del historial.
- Internacionalización, tema oscuro, notificaciones/toasts globales y adaptación responsive dedicada.
- Autenticación/autorización (401 como 4xx estándar).

## Criterios de finalización
- RF-1 a RF-4 verificados según EARS: historial 7 columnas `fecha|producto|proveedor|tipo|cantidad|motivo|id` con `EmptyState`/`Loading`/`ErrorMessage` (con `"—"` para `null`), sin filtros UI y sin paginación; alta `entrada` con `producto+proveedor+cantidad+motivo` y `salida` solo con `producto+cantidad+motivo` vía tabs `Entrada|Salida` preseleccionada, validación solo `cantidad>0 entero` (`/^-?\d+$/` + `Number.isInteger` tras `trim`, `"001"`→`1` válido, `"1.0"`→error local) y `motivo` no vacío tras `trim`, alta con `cargando` disabled y `4xx` sin Reintentar vs `5xx` con Reintentar, `201` cierra + banner `Movimiento registrado correctamente` 3s (`role="status"` posicionado sobre historial, reinicia timer si hay banner previo) + revalidación `GET` completa; si revalidación falla, coexistencia banner (arriba) + error (debajo).
- Selector de tipo conserva `producto/cantidad/motivo` al cambiar y limpia `proveedor` y errores al pasar a `Salida`; `<select>` solo activos ordenados por `codigo` con placeholder y `Cargando...` disabled, textura vacía bloquea `Crear` con mensaje puntual diferenciado por tipo, y fallo de carga muestra `ErrorMessage` dentro del modal (`401` sin Reintentar pero reintentable al reabrir, `5xx` con Reintentar).
- Mensajes de error usan dos niveles de `005` (4xx sin Reintentar vs red/5xx con Reintentar) y mensajes de éxito breves `role="status"` 3s separados, coexistiendo con error de revalidación si ocurre.
- Botones deshabilitados mientras `cargando`, sin duplicados locales; concurrencia y `stock insuficiente` vía `4xx` específico de API; `401` sin redirección.
- Sin filtros UI/paginación/edición/borrado/stock_actual/filtros fecha incluidos; `proveedor` nunca se envía en `salida`; fecha muestra ISO8601 UTC sin formateo.
- Pruebas de componente para historial, alta entrada, alta salida y manejo de estados con `fetch` mockeado según constitución frontend §4: `npm run test` verde y `npm run lint` sin errores.
- `npm run dev` muestra pantalla movimientos contra backend real con historial solo lectura, altas de entrada y salida funcionando, `selects` activos, revalidación visible, transición `0→1` y manejo `null` (`"—"`) vs `""` bloqueado.
- Spec aprobada sin [NECESITA ACLARACIÓN] bloqueante.

## Dudas abiertas
- Ninguna bloqueante. No hay puntos marcados como [NECESITA ACLARACIÓN]; paginación, filtros avanzados y valorización se evaluarán en specs futuras si se requieren.
